# Dossier: destroy-queue drain / notify helper (0xbc76e80)

## Mechanical facts
- [V] Large helper (rdis reported size field 0x2000 in sum range display, but disassembly/body extends; treat extent as function up to analyzed returns ~0xbc771ee). 34 blocks, 4 xrefs in. [I exact size bound uncertain from truncated view]
- [V] Touches queue object fields `a0+0x20/+0x28` (begin/end-like pointers), iterates/indexes entries (8-byte stride implied by `(end-begin)>>3` and indexed loads at +0/+8/+0x10/+0x18), computes a hash-like index using repeated `imul reg,0x1003F` mixing of bytes and `0x1007E0F81` constant.
- [V] Notifies external handler via `*(&data_12adf800)->vtable[1]` (slot 1) in multiple paths with args including entries from the queue; updates queue pointers/count at `a0+0x18` (dec) and compacts/moves 16-byte records (movups).

## A4-A8 relevance
- [V] Part of deferred destroy/resource-release machinery (used by Context frame/swap/shutdown paths per existing docs: `0xbc66de0` drains destroy queues including calls to 0xbc76e80; `0xbc660a0` uses related destroy helpers). Provides evidence that handle/resource destruction is mediated through queued entries and notifier callbacks on `data_12adf800`. [V call relation from existing dossiers/BGFX_MAP]
- [?] Precise queue element struct, hash bucket layout, and which resource handle classes it drains are not fully reversed here (needs deeper trace and cross-reference with 0xbc6f2a0/0xbc6f800 command consumers).
