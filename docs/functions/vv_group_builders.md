# Dossier: VV pass-group builders, resource declaration order and the pass-object Resources layout (1.26.62.01)

Agent passes-vv, 2026-11-14. Static only. Tools added: `tools/sigs/vvskel.py <lo> <hi>` (call/string/movabs skeleton) and `tools/sigs/vvstatics.py <fn rva>` (lazy name statics, where each is read, timeline of hashes/strings/vtables/key calls). Tags: [V] read in disassembly, [I] inferred, [?] open.

## The blocking fact, resolved [V]: textures are bound by NAME HASH, not by Resources field

The pass lambdas never read a texture field of `Resources`. Every named resource a builder touches (Color0, SceneDepth, Normal, ...) is a function-local lazy static: guard `G` (checked with `_Init_thread_header` 0xe938cb0 / `_footer` 0xe938d70), value at `G-8` = hash of the name string (string built with 0x79580; the hash loop is the 8-byte-stride FNV-style loop seen in the cold tail). A builder reads the 8-byte value (`mov reg,[rip+value]`) and puts it, with the texture handle, in a 0x28-byte binding record `{hash, ..., variant tag at +0x18}` appended to the pass's binding vector. So "declaration order" = the order of those reads in the builder; the names per pass are listed below. `vvstatics.py` prints them.

## The pass object and its Resources [V: 0xbc2c040 ctor, 0xbc2be20 Resources move-ctor, 0xbc2c2d0 dtor read in full]

Every deferred/water pass is one make_shared block of 0x348 bytes (control header 0x10, object 0x338, shared vtable rva 0xF0E9ED0):
- +0x00 vtable, +0x10 std::string (pass debug name), +0x38 inline std::function (execute thunk, ptr at +0x70, copied by the ctor), **+0x78 Resources (0x2A0 bytes)**, +0x318 std::string (material/pass name).
- Resources (offsets from the Resources base = what the execute body receives as `r8`, = pass+0x78) [V from 0xbc2be20]: `+0x00` u64, `+0x08` shared_ptr {ptr,ctrl} (moved; the "shared block"), `+0x18..+0x30` zeroed then a byte at +0x30, `+0x38` geometry reference 0x58 bytes (vertex-stream vector +0x40/+0x48/+0x50, count +0x58, index-buffer variant +0x60 with tag byte +0x70, startIndex +0x78, count +0x80, +0x88), `+0x90` MaterialInstance*, `+0x98` UniformBlock (0x78 bytes, copied by 0xe869ff0), `+0x110` owned pointer (moved), `+0x118` binding container (copied by 0x5669770, up to +0x23C), `+0x23C..+0x29C` 0x58 render-state block (copied in pieces +0x23C/+0x24C/+0x250/+0x254..+0x260/+0x264/+0x274/+0x283, qword +0x294).
  The bodies' reads of `+0x38/+0x90/+0x23C` quoted in material_pass_bodies.md match this layout; `+0x1A0` falls inside the +0x118 binding container, not a separate uniform block [I].
- The 0x120-byte config at `+0x08..+0x11C` of the object created by the first make_shared (size 0x130, vtables 0xF43F9E0 etc.) is the builder's fifth argument (`[rbp+0x11e0]`: view rect, four mat4, 16 bytes, byte +0x98), copied verbatim for every pass of the group.
