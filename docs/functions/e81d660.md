## Control flow / semantics [V]

1. Acquire the submit lock `sub_eec59f0(this+0x7850)`; nonzero -> fatal.
2. If `this->[0x789C] == 0x7FFFFFFF` (already aborted) -> set `0x7FFFFFFE`, fatal.
3. Advance a pair of ring cursors `this->[0x7840]`/`this->[0x7844]` modulo `this->[0x7838]`
   until a non-zero step is found (`0xe81d6e0..0xe81d73f`); commit `this->[0x7840]`.
4. `++this->counter[a2]` (`counter` at this+0x18, stride 24) and fill the per-slot record at
   index `tail = this->[0x783C]` (record at this+0x1820, stride 24):
   `[+0]=a2`, `[+0x10]=0 (byte)`, `[+0x04]=a3`.
5. CFG-guarded virtual call: target = `(*(void**)(a1->[0x30]))[0x1A8]`, invoked through the
   guard thunk `sub_eea6040` (data slot `0xF99FFA0`, a `jmp rax`), with
   `(rcx=a1->[0x30], rdx=this->[0x7828], r8d=2, r9d=tail*2)`.
6. Advance `this->[0x783C]` (tail) by `clamp(cur0 - tail)` modulo `this->[0x7838]`.
7. Release the lock `sub_eec5a10(this+0x7850)`; return `tail`.

The two cursor-adjust blocks (`0xe81d6e0..0xe81d73f` and `0xe81d798..0xe81d7ce`) are the
signed-modulo idiom `(x - y) + ((x-y)>>31 & mod)` followed by `clamp(...)` and `% mod`.

## Ownership / threading

`this+0x7850` is a lock object bracketing the read-modify-write of the ring cursors and the
guarded submit; the lock is taken via `sub_eec59f0` and released via `sub_eec5a10` on the
normal path. The error paths call `sub_eec5a00` (fatal, noreturn). Effects are CPU-visible
writes to the context struct plus the guarded virtual call (GPU submit), so V2 footprint
verification covers the struct writes; the submit itself is covered by V3.
